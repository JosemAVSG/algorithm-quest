# M05 — El registro de reparaciones

| Field | Value |
| --- | --- |
| id | `M05` |
| world | 1 |
| difficulty | 3 |
| primary concept | `C08` transform |
| secondary concept | `C05` collect |

| prerequisites | `M04` |
| est. time | 12–16 min |

**First mission where the output is not derived from the input by selection, but by
reshaping.** Up to here, elements went in and the same elements came out. Now they change.

---

## 1. Briefing (player copy, ES)

> **El registro de reparaciones**
>
> El registro del taller lo escribió alguien a mano durante años. Cada línea tiene el
> aparato, si se resolvió y cuántas horas costó, pero el panel nuevo no entiende ese
> formato.
>
> El panel necesita, para cada reparación:
>
> - `status`: `"closed"` si se resolvió, `"open"` si no.
> - `priority`: `"high"` si costó **más de 8 horas**, `"normal"` si no.
>
> Y necesita **todas** las reparaciones, en el mismo orden.
>
> El registro original no se puede tocar: es el archivo histórico y lo audita el
> contador.

**No se menciona:** transformación, `map`, objeto nuevo, inmutabilidad. La restricción
("el registro original no se puede tocar") introduce la inmutabilidad como requisito de
negocio, no como dogma.

---

## 2. Contract

```
normalizeRepairs(repairs: Repair[]) -> NormalizedRepair[]

Repair           = { id: string, device: string, resolved: boolean, hours: number }
NormalizedRepair = Repair & { status: 'closed'|'open', priority: 'high'|'normal' }
```

- One output element per input element. **Same length, always.**
- Order preserved.
- `priority` is `'high'` when `hours > 8`, strictly.
- Input array and its elements must be unchanged after the call.

---

## 3. Constraints

- Must return **new objects**, not the input objects with fields added.
- No `.map` (same scaffold rule; lifted after this mission).
- Must not reorder.

---

### Edge (3)

| # | Input | Expected | Catches |
| --- | --- | --- | --- |
| ED1 | `[{R9,resolved:false,hours:8.0001}]` | `priority:'high'` | `>=` instead of `>` |
| ED2 | `[{R10,resolved:false,hours:100}]` | `open/high` | long job, open |
| ED3 | five mixed repairs | correct order and values | index drift in the output |

### Invariant check (harness, not a test case)

Before the call, deep-freeze a copy of the input. After the call, deep-compare. Any
difference emits `E11` regardless of whether the tests passed. A player who mutates the
input but returns the right answer **fails the mission** — the briefing said the archive is
untouchable.

## 6. Common mistakes → diagnostics

| Player code | Code | Mentor says |
| --- | --- | --- |
| `repairs[i].status = ...; return repairs;` | `E11` | "La salida es correcta, pero el registro histórico cambió. El contador audita ese archivo. Necesitas objetos nuevos." |
| `const out = []; repairs.forEach(r => out.push(...))` sin `return out` | `E08` | "`forEach` no devuelve nada. Tu función devuelve `undefined`." |
| `return repairs.map(...)` | `E19` | "`.map` hace exactamente esto, y por eso está bloqueado en este ejercicio. Escríbelo con un bucle." |
| `if (hours >= 8) priority = 'high'` | `E05` | "Una reparación de exactamente 8 horas sale como `high`. El panel dice *más de* 8." |
| Devuelve solo las cerradas | `E07` | "El panel necesita todas, no solo las resueltas. ¿Cuántas entradas tiene tu salida y cuántas la entrada?" |
| `out.push({ status, priority })` (sin el resto) | `E12` | "Cada elemento de salida perdió `id`, `device` y `hours`. El panel los necesita." |

The first row is the important one: this is the first mission where a **passing solution is
rejected for a non-functional reason**. That is deliberate. The invariant is part of the
contract, and the mentor says exactly why.

## 7. Hint ladder

**L1**
> Si el registro original no se puede tocar, ¿puedes modificar cada reparación y devolver
> la misma lista? ¿Qué alternativa te queda?

**L2**
> Con `[{hours:12, resolved:true}]` tu salida no tiene `status` ni `priority`. Fíjate en
> qué objeto estás guardando: ¿el original, o uno nuevo que copia sus campos?

**L3**
```
crear lista vacía  resultado
para cada reparación original:
    status   = resuelta ? "closed" : "open"
    priority = horas > 8 ? "high" : "normal"
    nuevo    = { ...reparación original, status, priority }
    agregar nuevo a resultado
devolver resultado
```
La clave es `{ ...original, ... }`: copia los campos y añade los nuevos, sin tocar el
original.

**L4 — worked variant (isomorphic)**
> Un concesionario debe etiquetar cada coche del inventario como `"eléctrico"` o
> `"combustión"` y como `"premium"` o `"estándar"` según el precio, sin modificar la ficha
> original del vehículo.
> ```
> function etiquetarCoches(coches) {
>   const salida = [];
>   for (let i = 0; i < coches.length; i++) {
>     const c = coches[i];
>     const etiqueta = {
>       ...c,
>       motor: c.esElectrico ? 'eléctrico' : 'combustión',
>       gama: c.precio > 40000 ? 'premium' : 'estándar'
>     };
>     salida.push(etiqueta);
>   }
>   return salida;
> }
> ```

## 8. Debrief

### Why it works
Transformar no es seleccionar. En M03 el criterio decidía *si* un elemento entraba; aquí
todos entran y cada uno cambia de forma. Por eso la salida tiene siempre la misma longitud
que la entrada — si no la tiene, hay un `if` de más en algún sitio.

### Why the input must stay untouched
Mutating the input is the single most expensive habit in real code: it makes a function's
effect invisible to whoever calls it, and it breaks any caller that reuses the data. Here
the cost is a fictional audit; in production it is a bug that appears three files away.

### Edge cases
`hours = 8` is the boundary, and it is *not* high. Same shape as M01's `>` vs `>=`, now
applied to a field inside an object. The lesson transfers; the surface changed.

### Cost
`O(n)`, one pass, one object allocation per element. The allocation is the real cost here —
and in M09 we start measuring costs instead of naming them.

### Real world
DTO mapping, API response shaping, ETL transforms, `SELECT ... AS ...` projections, view
models in any frontend.

### Reasoning prompt
> ¿Por qué la salida tiene el mismo número de elementos que la entrada? ¿Qué tendría que
> cambiar en el enunciado para que ya no fuera así?

`objectiveNouns`: `registro`, `panel`, `reparación`, `histórico`
`reasoningLexicon`: `transformo`, `copio`, `creo`, `conservo`

## 9. Mastery & transfer

- `C08` primary, `C05` secondary.
- `C08` transfer: M11, where the transformation is a projection into a *key* rather than a
  new object — the same idea with a different output shape.
- Mutation (`E11`) is tracked as a behavioural signal but does not have its own concept ID.
  It contributes to `C08` robustness, because immutability is part of the transform
  contract.

## 10. Reward

`sys.log`: **broken → working**. The repair log panel becomes searchable and colour-codes
high-priority jobs.

## 11. Anti-drift notes

- Do not introduce `map` here. The whole point is that the loop *is* the transform, and the
  player should feel that `.map` is a convenience, not a different idea. M10 does the same
  for `Set`.
- The mutation check is the first non-functional rejection in the product. It must be
  explained in the briefing (it is) and in the diagnosis (it is). Never surprise a player
  with a rule that was not stated.
