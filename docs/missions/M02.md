## 1. Briefing (player copy, ES)

> **Cuarenta sensores, una pregunta**
>
> Ya arreglaste el sensor del horno. Ahora el taller tiene cuarenta sensores en la línea
> y el jefe de turno no quiere un informe: quiere saber **una sola cosa** antes de
> arrancar. Si hay un solo sensor por encima del límite, la línea no arranca.
>
> Tienes la lista de lecturas y el límite. Dime si hay que parar.
>
> Y no me hagas revisar los cuarenta si el primero ya está mal — cada segundo que la
> línea está parada cuesta dinero.

**No se menciona:** recorrido, bucle, `return` temprano, `for`. La restricción de negocio
("no revises los cuarenta si el primero ya está mal") es la que introduce la idea sin
nombrarla.

## 2. Contract

```
anyDeviceFaulty(readings: number[], limit: number) -> boolean
```

- `true` if **at least one** reading exceeds `limit`.
- `false` if the array is empty, or if no reading exceeds `limit`.
- Equality is not a fault (consistent with M01).
- Must always return a boolean.

---

## 3. Constraints

- Must not mutate `readings`.
- Must not use `Math.max`, `.some`, `.filter`, `.find`, or any array method that hides the
  iteration. **The point of the mission is the loop.** The harness rejects these calls with
  a specific diagnostic (`E_CONSTRAINT`), not a test failure.

> **Why ban `.some`?** Because `.some` is the correct answer, and if it is available the
> mission teaches nothing. This is the only mission in World 1 with a construct ban, and it
> is lifted immediately after. It is honest about being a scaffold.

## 6. Common mistakes → diagnostics

| Player code | Code | Mentor says |
| --- | --- | --- |
| `for (let i = 0; i < readings.length - 1; i++)` | `E06` | "Tu bucle termina una posición antes. ¿Qué pasa si el único sensor defectuoso es el último de la lista?" |
| `for (let i = 0; i <= readings.length; i++)` | `E06` | "En la última vuelta `readings[i]` no existe. ¿Cuántas posiciones tiene realmente el array?" |
| `if (readings[i] > limit) return true;` **sin** `return false` al final | `E08` | "Cuando ningún sensor está mal, ¿qué devuelve tu función? Compruébalo con `[80, 88]`." |
| `return readings[0] > limit` dentro del bucle | `E07` | "Con `[100, 80]` aciertas, pero con `[80, 100]` no. Tu función decide con el primer elemento y no mira el resto." |
| `.some(...)`, `.filter(...)`, `.find(...)` | `E_CONSTRAINT` | "Ese método hace el recorrido por ti, y este ejercicio trata sobre el recorrido. Escríbelo con un bucle." |
| `readings.sort()` antes de recorrer | `E11` | "Ordenaste la lista original. El resto del taller sigue usando esa lista. ¿Puedes resolverlo sin tocarla?" |

### Detection note: the rotation probe

`E07` (premature exit) is detected deterministically by running the player's function a
second time on a **rotated** copy of the same input. If `f([a,b,c]) !== f([c,a,b])` for a
set where the answer must be invariant under rotation, the function is not examining all
elements. This is a five-line check and it beats any attempt to infer intent from source.

## 7. Hint ladder

**L1**
> ¿Tienes que revisar todos los sensores siempre, o hay un momento en el que ya sabes la
> respuesta y puedes parar? ¿Cómo se llama esa situación en tu código?

**L2**
> Con `[80, 88, 95]` y límite 90, tu función devuelve `false`. Recórrela a mano: ¿en qué
> vuelta debería haber cambiado la respuesta, y en cuál se quedó?

**L3**
```
para cada lectura de la lista:
    si la lectura supera el límite:
        devolver true      ← ya sabes la respuesta, no sigas
después del bucle (nadie superó el límite):
    devolver false
```
Fíjate en que hay **dos** `return`, y en que el segundo está fuera del bucle.

**L4 — worked variant (isomorphic)**
> Un almacén revisa si algún paquete de un envío está dañado. Si encuentra uno, el envío
> se rechaza sin revisar el resto.
> ```
> function envioTieneDanado(paquetes) {
>   for (let i = 0; i < paquetes.length; i++) {
>     if (paquetes[i].danado) {
>       return true;
>     }
>   }
>   return false;
> }
> ```
> El `return false` final solo se alcanza si el bucle terminó sin encontrar nada.

## 8. Debrief

### Why it works
La función tiene dos salidas posibles y ambas son correctas: salir en cuanto se demuestra
que hay un fallo, o salir al final cuando se demuestra que no lo hay. La clave es que el
`return false` esté **fuera** del bucle. Si está dentro, la función responde tras mirar un
solo elemento.

### The structural idea
Un bucle con retorno temprano tiene siempre la misma forma: *buscar → salir con éxito →
salir con fracaso*. Cambia el predicado, cambia el tipo de retorno, pero la forma no.
Vas a reutilizarla en M07 y en M12.

### Edge cases
Lista vacía → `false`, porque "hay algún defecto" es falso cuando no hay elementos. Es el
caso que más gente rompe, y es el que separa "recorrí la lista" de "la lista existe".

### Cost
Peor caso: `n` comparaciones. Mejor caso: 1. En promedio, la mitad. Esto es `O(n)` — y
ahora mismo no importa, porque `n = 40`. En M09 vas a ver qué pasa cuando `n` no es 40.

### Real world
`Array.prototype.some`, validación de formularios, cortocircuito en reglas de negocio,
`anyMatch` en Java streams, `EXISTS` en SQL. Todos son esta misma función.

### Reasoning prompt
> Explica por qué hay dos `return` y por qué el segundo no puede estar dentro del bucle.
> Después di qué devuelve tu función con una lista vacía y por qué eso es correcto.

`objectiveNouns`: `línea`, `sensor`, `fallo`, `parar`
`reasoningLexicon`: `recorro`, `paro`, `encuentro`, `devuelvo`

## 11. Anti-drift notes

- The construct ban is temporary and must be **visible in the UI**, not just in the tests.
  A player who is failed for using `.some` without being told is being punished for being
  right.
- If more than 60% of players solve this on attempt 1, H2 is too easy to hit by accident
  and should be replaced by a case where the fault is at the last index *and* the array
  has an even length (defeats "check every other element" heuristics).
