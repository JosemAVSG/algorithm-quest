**This mission is the deliberate inverse of M02.** Same input shape, opposite loop
discipline. If a player does not feel the contrast, World 1 has failed.

---

## 1. Briefing (player copy, ES)

> **El lote del proveedor**
>
> El jefe de turno cambió de opinión. Ya no quiere saber *si* hay que parar: quiere la
> **lista completa** de las unidades defectuosas para devolverlas al proveedor.
>
> Necesita los identificadores y la temperatura de cada una, en el mismo orden en que
> llegaron, para que coincida con la factura.
>
> Ojo: no puedes devolver solo la primera. El proveedor rechaza la devolución si la lista
> está incompleta.

**No se menciona:** acumular, `push`, array de resultados. La restricción de negocio
("el proveedor rechaza la devolución si la lista está incompleta") es la que define el
problema.

---

## 2. Contract

```
collectFaultyDevices(devices: {id: string, temperature: number}[], limit: number)
  -> {id: string, temperature: number}[]
```

- Returns every device whose `temperature` **exceeds** `limit`.
- Preserves input order.
- Returns `[]` when nothing matches or the input is empty.
- Must not mutate `devices` or its elements.

---

## 3. Constraints

- No array methods that hide iteration (`.filter`, `.map`, `.reduce`). Same scaffold rule
  as M02, lifted after this mission.
- Must return a new array, never the input array.

### Edge (3)

| # | Input | Expected | Catches |
| --- | --- | --- | --- |
| ED1 | `([{id:'A',temperature:90}], 90)` | `[]` | equality is not a fault |
| ED2 | `([{id:'A',temperature:95}], 90)` | `[A]` | singleton match |
| ED3 | `([{id:'A',temperature:90},{id:'B',temperature:90}], 90)` | `[]` | all-at-limit |

H4 exists specifically to break the "return after the first push" pattern — the player who
wrote `return result` inside the `if` gets one element instead of three, and the diff is
visually obvious.

## 6. Common mistakes → diagnostics

| Player code | Code | Mentor says |
| --- | --- | --- |
| `return result;` **dentro** del `if` | `E07` | "Con tres unidades defectuosas devuelves una. ¿En qué momento decides que ya terminaste?" |
| `result.push(i)` (índice en vez de elemento) | `E12` | "Estás guardando posiciones (`0`, `2`), pero el proveedor pide las unidades con su `id` y su temperatura." |
| No `return result` al final | `E08` | "Cuando ninguna unidad falla, tu función devuelve `undefined` en vez de una lista vacía." |
| `devices[i].temperature = limit` al marcar | `E11` | "Modificaste la lista original. El resto del taller la sigue usando. Devuelve una lista nueva." |
| `return devices` sin filtrar | `E12` | "Devuelves todas las unidades. ¿Cuáles son las defectuosas?" |
| `result = result.concat(...)` dentro del bucle con `result` declarado con `let` fuera | ✅ | *Correct, if inefficient. Not a diagnostic. The mentor says nothing.* |

That last row matters. A correct-but-suboptimal solution in a mission without an
efficiency budget must not trigger feedback. Silent acceptance is a feature.

## 7. Hint ladder

**L1**
> En M02 podías parar en cuanto encontrabas un fallo. Aquí, ¿puedes parar alguna vez
> antes de terminar la lista? ¿Por qué?

**L2**
> Con tres unidades defectuosas tu función devuelve una. Mira dónde está tu `return` y
> pregúntate: ¿qué queda sin revisar después de esa línea?

**L3**
```
crear una lista vacía  resultado
para cada unidad de la lista:
    si la unidad supera el límite:
        agregar la unidad a resultado      ← sin return
al terminar el bucle:
    devolver resultado
```

**L4 — worked variant (isomorphic)**
> Un turno de soporte arma la lista de tickets que llevan más de 48 horas abiertos, para
> escalarlos todos juntos.
> ```
> function ticketsVencidos(tickets) {
>   const vencidos = [];
>   for (let i = 0; i < tickets.length; i++) {
>     if (tickets[i].horasAbierto > 48) {
>       vencidos.push(tickets[i]);
>     }
>   }
>   return vencidos;
> }
> ```
> La diferencia con el ejercicio anterior es que no hay `return` dentro del `if`.

## 8. Debrief

### Why it works
La función no responde una pregunta binaria: **construye un valor**. Eso obliga a recorrer
la lista completa, porque cada elemento puede añadir algo al resultado. El `return` vive
fuera del bucle porque el resultado no está completo hasta que el bucle termina.

### The contrast with M02
| | M02 | M03 |
| --- | --- | --- |
| Pregunta | ¿existe alguno? | ¿cuáles son todos? |
| Puede parar antes | sí, al primer match | no |
| Retorno | `boolean` | `array` |
| `return` dentro del bucle | correcto | error |
| Peor caso | `n` | `n` |

Mismo costo, distinta disciplina. Reconocer cuál de las dos formas pide un problema es la
habilidad de la misión.

### Edge cases
Lista vacía → `[]`, no `undefined`. Es el mismo error que en M02 pero con otra forma, y
es el que más veces se repite en producción: una función que devuelve "nada" en vez de
"una colección vacía" obliga a quien la llama a defenderse.

### Cost
`O(n)` siempre, sin atajos. No hay mejor caso: incluso si el primero ya está mal, hay que
seguir mirando.

### Real world
`Array.prototype.filter`, `WHERE` en SQL, reportes de incidencias, generación de listas de
exclusión, recolección de errores de validación en un formulario.

### Reasoning prompt
> ¿Por qué el `return` no puede estar dentro del `if`? Explica qué se pierde si lo mueves
> ahí, usando un ejemplo con dos unidades defectuosas.

`objectiveNouns`: `lista`, `unidades`, `proveedor`, `devolución`
`reasoningLexicon`: `acumulo`, `agrego`, `recorro`, `completo`

## 11. Anti-drift notes

- Do not merge M02 and M03 into one mission "with two functions". The contrast is the
  lesson, and it needs two separate briefing→debrief cycles.
- Do not add "optimize this" to M03. It is `O(n)` and there is nothing to optimize. The
  temptation to add a challenge here is the temptation to turn the product into a list.
